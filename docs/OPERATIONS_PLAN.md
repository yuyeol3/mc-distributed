# 빠른 장애 인수·월드 교체·플러그인 관리 구현 계획

상태: 기본 기능 구현 및 로컬 검증, 2026-10-27. 사용자는 빠른 복구를 우선한다.
VPN/SSH 원격 환경과 OS/VM 정지는 추가 검증 대상이다. 아래 내용은 원래의 설계 기준이며 실제 구현 차이는 다음 절에 기록한다.

## 구현 결과와 범위

- GUI의 월드·플러그인 관리와 CLI의 `world replace/backups/restore`, `plugin list/add/remove`를 구현했다.
- `GUARDED`는 Paper 실행 전의 인수 대기까지 포함한다. 별도의 STARTING 락 상태를 추가하지 않고 Node 상태로 표시한다.
- 식별자는 로컬 `.git/mcd-node-id`에 보존한다. 같은 사본은 OS 파일 락으로 배타 실행하고 epoch로 호스트 기간을 구분한다. 다른 PC의 같은 표시 이름은 소유권을 얻지 못한다.
- 플러그인 JAR 목록·해시는 `mcd-plugins.properties`로 공유한다. 일반 스냅샷은 JAR 변경을 stage하지 않고, 검증된 관리 작업에서만 명시적으로 stage한다.
- 가져오기는 `level.dat`의 정식 버전 이름을 읽는다. 신규/임의 버전의 data-version 상한을 독립적으로 계산하는 기능, 싱글플레이 인벤토리 변환, 옛 Paper/Spigot의 분리 차원을 26.1 이상으로 변환하는 기능은 포함하지 않는다. 변환이 필요한 경우 사전에 변환한 사본을 사용한다.
- 파일로 확인 가능한 플러그인 요구사항을 검사하지만 실제 활성 상태는 호스트 콘솔의 `plugins`로 확인한다. 자동 활성 상태 파서·원격 관리 RPC는 추가하지 않았다.
- 로컬 장애 후 접속 완료 56.229초·74.008초, 소유권 상실 후 이전 Paper 종료 2.552초·5.727초를 관찰했다. Paper 26.2에서 실제 생성한 월드·컴파일한 최소 플러그인을 다른 사본으로 전달해 기동했다. 상세 조건은 [E10](../experiments/E10-results.md)에 기록한다.
- 관리 창은 격리한 Swing 미리보기를 PNG로 렌더해 배치를 확인했다. Windows UI 자동화 도우미의 native pipe 연결이 실패해 실제 클릭 흐름 자동화는 수행하지 못했다.

## 목표와 범위

- writer 장애를 VPN으로 빠르게 감지하고, Git 소유권 인수와 기존 writer의 자동 종료를 연결한다.
- 기존 월드를 폴더 또는 ZIP으로 교체하고, 변경 전 상태로 복구할 수 있게 한다.
- 플러그인 JAR를 추가·교체·제거하고 모든 호스트가 같은 파일로 실행되게 한다.
- 별도 상시 서버, 플러그인 마켓 검색, 자동 업데이트, 실행 중 플러그인 reload는 첫 범위에서 제외한다.
- 초기 관리 작업은 월드가 사용 중이면 거절한다. 이 PC의 서버도 일반 종료 시 자동 이관하는 경로를 재사용해 끄지 않는다.

## 현재 구현에서 재사용할 부분

| 코드 | 재사용 및 변경점 |
|---|---|
| `lock/HostLock` | force 없는 push 경쟁, epoch, recovery. 기대한 소유권을 조건으로 한 조기 인수 추가 |
| `lock/LockState` | 플레이 소유권과 관리 작업 상태, 실행 세션 식별자·상태 확인 주소 추가 |
| `node/Node`, `HostSession` | 관찰·라우팅·호스트 수명 관리. 긴 Git/저장 작업과 상태 확인 분리 |
| `net/Tailnet`, `net-helper/main.go` | 기존 SOCKS 연결 재사용, 상태 확인용 포트도 tailnet에 노출 |
| `server/ParentWatchdog`, `PaperServer` | 부모 종료 감시를 확장해 실행 허가 만료 감시, 제한 시간 뒤 강제 종료 |
| `cli/UpgradeCommand` | 락 획득 → 변경 → 반납의 형태 참고. 긴 관리 작업의 락 갱신은 추가 필요 |
| `world/WorldTemplate` | 기존 repo를 포함한 ignore 규칙 이행, 월드 형식·기능 버전 기록 |
| `gui/MainWindow` | 기존 control 작업 큐와 월드 선택 UI에 관리 기능 연결 |

표의 패키지 경로는 `src/main/java/mcd/` 기준이다. 서비스는 GUI·CLI가 공유하며 범용 작업 프레임워크는 만들지 않는다.

## 1. 빠른 writer 장애 감지와 인수

### 시간 값의 초기 가설

| 항목 | 초기값 | 의미 |
|---|---|---|
| VPN health 요청 | 5초 간격, 요청 전체 제한 2초, 중첩 없음 | SOCKS 협상·연결·응답 모두 제한 |
| 장애 의심 | 연속 3회 실패 | 보통 장애 후 약 15~20초 이내. 1회 성공하면 초기화 |
| writer의 Git 소유권 조회 | 5초 간격, 요청 전체 제한 3초 | 월드 fetch 대신 원격 ref 조회 우선 |
| writer 실행 허가 | 확인 요청 시작 시각부터 최대 20초 | 늦게 도착한 응답으로 허가가 연장되지 않음 |
| 허가 만료 후 종료 | 최대 5초, 이후 강제 종료 | 평소 2분 graceful stop과 분리 |
| 새 writer 기동 전 대기 | 인수 push 성공 후 최소 30초 | 이전 허가 20초 + 종료 5초 + 여유 5초 |

초기 목표는 장애 인식 15~20초, 인수 후 새 Paper 기동 시작까지 총 45~60초다.
Paper 준비 완료는 여기에 JVM·월드 로딩 시간이 더해진다. 느린 Git/네트워크에서는 상한을 보장하지 않는다.
기존 Git heartbeat 2분, 스냅샷 10분, 빈 서버 종료 5분은 유지한다. `Timing`의 TTL 비례 관계를 필요한 곳만 분리한다.

### 감지와 소유권 인수 절차

1. 상태 응답은 월드 식별자, 프로토콜 버전, 실행 세션 ID, owner, epoch, 상태를 포함한다.
   상태는 기동 중·플레이 가능·인수 대기·종료 중·관리 작업을 구별한다. 이름이 같은 PC도 다른 세션으로 취급한다.
2. handler는 메모리 상태만 읽는다. 요청마다 Git이나 Paper 명령을 실행하지 않는다.
   Paper 기동 중은 장애로 보지 않는다. 기동 시간 초과·Paper 종료는 별도로 처리한다.
   프로세스가 살아 있지만 게임 tick만 멈춘 장애까지 탐지하는 기능은 초기 범위에서 제외한다.
3. 연속 실패를 확인한 후보가 Git 최신 상태를 다시 읽는다. 관찰한 세션·epoch가 달라졌으면 판단을 폐기한다.
   health 정보가 없는 옛 노드는 기존 TTL로만 인수한다. Git에 접근할 수 없으면 새 인수를 하지 않는다.
4. 최신 원격 커밋 위에 다음 epoch의 인수 대기 상태를 push한다. 동시 후보 중 성공한 하나만 진행한다.
   변경된 원격 상태를 무시한 강제 인수, force push, 다른 후보 실패 후 무조건 재시도는 하지 않는다.
5. 성공한 후보도 곧바로 Paper를 띄우지 않는다. 최소 30초를 기다리며 자신의 소유권과 health 응답을 유지한다.
   대기 후 원격 소유권을 다시 확인하고 마지막 공유 스냅샷으로 시작한다.
6. 기존 writer는 소유권 변경, push 거절, 실행 허가 만료 시 플레이를 중단한다.
   이전 epoch의 변경은 main에 재적용하지 않고 기존 recovery 경로로 보존한다.

소유권 확인은 작업 트리를 바꾸지 않는 별도 경로로 구현한다. 현재 `HostLock.peek()`는 호스트에서 사용할 수 없다.
검증한 ref와 로컬 성공 push 계보를 비교하고, 모르는 ref는 해당 커밋의 락을 별도로 읽는다.
원격 조회와 허가 갱신은 순차 처리해 늦은 응답이 최신 관찰을 덮지 못하게 한다.
긴 스냅샷·Git 호출이 확인 스레드나 종료 감시를 막아서는 안 된다.

### 기존 writer를 멈추는 조건과 한계

- Paper 쪽 watchdog이 유효한 원격 확인을 근거로 한 허가 만료를 독립적으로 감시한다.
  mcd가 단순히 살아 있거나 VPN 요청에 응답한다는 이유만으로 허가를 연장하지 않는다.
- 정상 종료가 완료되지 않으면 외부 프로세스 감시에서 강제 종료한다. 감시 자체가 멈추는 경우도 실험한다.
- 단조 시간, 요청 시작 시각, 실제 프로세스 종료를 사용해 순서와 시간 예산을 검증한다.
  절전·재개, 전체 VM 정지, 장시간 JVM 정지에서는 동일한 시간 보장을 당연하게 가정하지 않는다.
- Git main에 반영되는 계보는 하나로 유지한다. 임의의 OS/프로세스 정지 상황까지 Paper 동시 실행이
  절대로 없다고 주장하지 않는다. 검증된 실행 환경에서 이전 Paper가 새 Paper보다 먼저 멈추는 것을 출시 기준으로 삼는다.
- Git 장애가 20초 이상 지속되면 정상 writer도 멈춘다. 빠른 인수를 위한 의도적인 가용성 비용이다.
  장애 인수는 저장 주기를 줄이지 않으므로 마지막 스냅샷 이후 최대 10분의 진행은 복원하지 못할 수 있다.
- 죽은 Paper에서 클라이언트에 transfer를 보낼 수는 없다. 장애 후 사용자는 재접속할 수 있어야 하며,
  자동 재접속까지 지원한다고 표시하지 않는다. 로그인 대기 중에는 바뀐 호스트로 라우팅을 다시 계산한다.
- 평소에는 health만으로 무인 서버를 시작하지 않는다. 접속 요청 또는 장애 시점의 실제 접속 수요가 있는 노드만 인수 후보가 된다.

### 호환성과 배포

빠른 인수를 켜기 전에 모든 참가 PC를 종료하고 새 버전으로 맞춘다. 옛 writer의 기존 lease 종료도 고려한다.
새 프로토콜·관리 상태를 월드에 기록하고 새 앱은 지원 범위를 검사한다.
최소 앱 버전 필드만으로 이미 배포된 옛 프로그램을 통제할 수 있다고 가정하지 않는다.
혼용 상태에서는 조기 인수를 활성화하지 않는다.

## 2. 월드·플러그인 변경의 공통 절차

1. 입력 검증과 압축 해제는 git 작업 트리 밖 임시 폴더에서 수행한다.
2. 최신 원격 락이 FREE일 때만 관리용 락을 획득한다. 같은 표시 이름의 다른 세션도 사용 중으로 판단한다.
3. 관리 상태에서는 다른 PC의 로그인·호스팅을 막고 변경 중임을 표시한다.
   Paper가 없다고 unhealthy로 인수하지 않는다. 오래 걸리는 작업은 락을 갱신하고, 만료 시 다른 노드가 작업 전 main으로 복구한다.
4. 변경 전 공유 상태를 명명된 backup ref로 원격에 보존한다. 백업 push가 성공해야 교체를 시작한다.
5. 검증한 파일만 적용하고, 변경 내용과 FREE 상태를 하나의 커밋으로 push한다.
   서로 다른 파일 세트를 조합해서 클라이언트에게 공개하지 않는다.
6. 실패·중단 시 입력과 백업을 보존하고 성공으로 표시하지 않는다. 원격 결과가 불명확하면 다시 조회해 확정한다.
   미완성 파일을 일반 startup recovery가 main으로 자동 push하지 않도록 작업 기록과 복구 경로를 둔다.
7. 복구는 백업 내용을 새로운 커밋으로 적용한다. main을 과거로 force reset하지 않는다.

긴 작업의 heartbeat는 일반 writer 스레드와 같은 작업 트리에서 병렬 커밋하지 않는다.
검증·추출을 선행하고 Git 변경을 직렬화하며, 락을 잃은 뒤에는 publish하지 않는다.
GUI는 변경 전 파일 선택·검증 결과·백업·영향 범위를 보여 주고 최종 적용 단계에서 확인한다.
이 최초 버전에는 실행 중인 원격 서버를 강제로 종료하는 관리 RPC를 넣지 않는다.

## 3. 월드 교체

### 사용자 흐름과 첫 지원 범위

월드 관리 → 월드 교체 → 폴더 또는 ZIP 선택 → 감지 결과 확인 → 백업 후 적용.
등록된 다른 repo로 전환하는 기존 기능과 구별한다. 현재 repo·초대·VPN 설정은 유지한다.

- 첫 지원은 Vanilla 싱글플레이 월드와 대상 버전에 맞는 Paper 월드다. 임의의 서버 폴더 전체는 가져오지 않는다.
- `level.dat`의 정식 버전 이름과 차원 구조를 읽어 현재 Paper보다 새 월드는 거절한다.
  원본은 보존하며, 구버전의 실제 변환은 지원되는 경우 다음 Paper 기동 시 수행한다. 일반적인 모든 구버전 조합의 변환을 검증했다고 표시하지 않는다.
- 현재 기본 26.2와 테스트의 26.1.2 구조를 먼저 fixture로 검증한다.
  과거의 world_nether/world_the_end 구조를 모든 버전에 일괄 적용하지 않는다.
- 오버월드·네더·엔드·월드 소속 플레이어 데이터·datapack을 교체 대상으로 명시한다.
  이전 월드의 남은 차원 파일과 플레이어 데이터가 새 월드에 섞이지 않게 한다.
- singleplayer 주인의 `level.dat` 내 플레이어 상태와 서버 UUID 플레이어 파일의 차이도 확인한다.
  인벤토리 자동 이관을 검증 없이 보장하지 않는다.
- 플러그인, 권한 목록, 서버 운영 설정은 유지한다. 외부 입력의 `.git`, mcd 설정, 인증 정보, 서버 JAR는 반입하지 않는다.
  월드별 데이터를 갖는 플러그인의 기존 데이터는 자동 초기화하지 않으며 적용 화면에 남는 범위를 표시한다.
- 첫 버전은 기본 월드 이름 `world`를 지원한다. custom level-name, 모드 전용 월드, 다중 월드 플러그인 맵은 거절한다.
- ZIP 경로 이탈, 절대 경로, 링크, 중복/대소문자 충돌 경로, 과도한 해제 크기·파일 수를 검증한다.
  원본 폴더를 수정하지 않고, Git 단일 파일·전체 push 크기도 적용 전 확인한다.

CLI 후보: `world replace --source <폴더|zip>`, `world backups`, `world restore --backup <ID>`.
첫 복구 범위는 이 기능이 만든 관리 작업 백업이며 범용 Git 이력 브라우저는 만들지 않는다.

## 4. 플러그인 관리

### 배포 방식

첫 버전은 사용자가 선택한 로컬 JAR를 월드 repo에 직접 저장한다.
별도 다운로드 서버·URL manifest·Git LFS를 추가하지 않고 기존 Git 동기화를 재사용한다.
repo 이력 용량은 늘어나므로 파일·전체 전송 크기를 사전 검증하고 관리 화면에 표시한다.

- 신규·기존 월드의 ignore 규칙에 `/plugins/*.jar`만 예외 허용한다.
  Paper JAR, `/plugins/.paper-remapped/` 등 생성 캐시, spark/bStats 캐시는 공유하지 않는다.
- JAR를 실행하지 않고 descriptor를 읽어 Bukkit/Paper 플러그인 여부, 이름, 버전, 요구 API,
  명시된 필수 의존성 및 중복 ID를 검사한다. 실제 런타임 호환성까지 확정한다고 표시하지 않는다.
- 같은 ID의 JAR 교체 시 이전 파일을 제거해 중복 로딩을 막는다. 필수 의존성이 있는 플러그인의 제거도 검증한다.
- 호스트 시작 전에 관리되는 JAR의 SHA-256과 실제 파일을 비교한다.
  ignore된 로컬 전용 JAR·이전 버전이 있으면 알리고 시작을 막아 PC별 플러그인 차이를 방지한다.
- 관리 상태의 파일 변경은 Paper가 완전히 꺼진 동안만 한다. reload·자동 업데이트는 제공하지 않는다.
- GUI 목록은 배포 파일 상태와 실제 활성 상태를 구별한다. Paper 시작 완료만으로 플러그인 활성 성공을 판단하지 않는다.
  최소 테스트 플러그인과 실제 콘솔의 활성 목록/오류를 통해 로딩 결과를 표시한다.
- 첫 보장 범위는 JAR 및 정적 설정의 동일성이다. SQLite·외부 DB·비동기 저장을 쓰는 임의 플러그인의
  데이터 무손실 스냅샷/이관은 별도 검증 대상이다. 현재 save-off만으로 이 데이터의 정합성을 보장하지 않는다.
- 제거 시 데이터 폴더는 보존한다. 실패한 설치 후 백업 복구는 명시적으로 수행한다.
  플러그인이 기동하며 바꾼 설정·월드까지 JAR만 되돌리면 복구된다고 가정하지 않는다.

GUI: 플러그인 관리 → 목록, JAR 추가, 같은 플러그인 교체, 제거, 로딩 결과 확인.
CLI 후보: `plugin list`, `plugin add --file <jar>`, `plugin remove --name <ID>`.
플러그인은 참가자의 PC에서 실행되므로 설치 화면에 다른 호스트에도 적용됨을 분명히 표시한다.

## 5. 구현 순서와 완료 기준

| 순서 | 작업 단위 | 완료 기준 |
|---|---|---|
| 1 | 장애 감지·펜싱 실험 | 시간 예산, 원격 조회 비용, mcd 정지·절전 복귀 시 종료 경로 확인 |
| 2 | 실행 세션·새 락 상태·watchdog | 늦은 응답·동명이인·긴 Git 호출에도 잘못된 실행 허가를 연장하지 않음 |
| 3 | VPN health·조기 인수·라우팅 | 동시 후보의 승자 하나, 이전 Paper 종료 뒤 새 Paper 시작, 실제 시간 기록 |
| 4 | 관리 락·백업·실패 복구 | 관리 중 접속 차단, 장기 작업 갱신, 크래시 뒤 부분 변경 자동 게시 방지 |
| 5 | 월드 교체·백업 복구 CLI | 세 차원·플레이어 데이터 일관 교체, 원본 보존, 두 번째 PC가 같은 월드로 시작 |
| 6 | 플러그인 관리 CLI·기존 repo 이행 | 두 PC의 JAR hash 일치, 제거·교체 후 잔존 JAR 없음, 실제 로딩 확인 |
| 7 | GUI와 사용자 문서 | 선택→미리보기→적용→실패/복구 흐름 확인, 혼용 버전 배포 절차 작성 |

규칙 테스트는 기존 JUnit·가짜 시계·실제 로컬 bare repo를 사용해 실패부터 확인한다.
새 테스트 라이브러리나 범용 DI 계층은 도입하지 않는다. GUI 배치는 실제 창으로 확인한다.

필수 장애 시나리오:
- 순간 VPN 끊김 후 복귀, VPN만 장기 단절, writer만 Git 단절, 전체 Git 단절.
- health 서버만 응답하지만 mcd 관리 스레드가 멈춤, Paper만 종료, 기동 지연.
- 이전 원격 응답의 지연 도착, 스냅샷 push와 인수 경쟁, 후보 둘의 동시 인수와 승자의 재크래시.
- 관리 작업 중 종료·인수·백업 실패·push 결과 불명확·같은 표시 이름의 PC 두 대.
- ZIP 경로 이탈·잘못된 월드 버전·네더/엔드 혼합 방지·복구 후 다른 PC에서 재개.
- 잘못된 JAR·중복 ID·누락 의존성·플러그인 초기화 실패·로컬에만 남은 JAR.

각 구현 단계는 관련 `./gradlew.bat test`를 실행하고, 프로세스·호스트 이관 변경에는 실제 Paper 시나리오를 실행한다.
26.2는 봇 지원을 가정하지 않고 콘솔/정품 클라이언트 검증을 병행한다.
시간 값 조정에 쓴 케이스 외에 별도 VPN 지연·절전·원격 친구 환경에서 오탐과 복구 시간을 측정한다.
기록: 장애 시점, 연속 실패 확정, 인수 push 완료, 기존 Paper 종료, 새 Paper 시작/준비 완료,
오탐 횟수와 Git 읽기/쓰기 횟수. 검증 전 45~60초를 보장 수치로 문서화하지 않는다.
