# E1′: 스냅샷 커밋 시간이 월드 크기에 따라 늘어나는 원인

E3에서 저장을 멈춘 동안 하는 로컬 커밋이 월드 파일 65개 2.3초 → 145개 16초로 늘었다.

## 방법

- `RecordSessionExperiment`: 실제 Paper와 봇으로 스냅샷 20개짜리 세션을 bare repo로 기록한다. 조정용(`tuning`: x축 400블록 간격, 7×7×7 건축)과 검증용(`validation`: z축 250블록 간격, 13×13×13 건축)을 따로 기록했다.
- `SnapshotCostAnalysis`: 기록한 스냅샷을 새 repo에 차례로 재생한다(내용이 바뀐 파일만 다시 쓴다). 스냅샷마다 바뀐 파일, 커밋 시간, push 시간을 잰다. Paper 없이 반복할 수 있다.
- 원인 분석과 개선은 조정용으로만 하고, 검증용은 마지막 확인에만 썼다.

## 결과

**스냅샷 하나에서 바뀌는 양은 거의 일정했다**(조정용: region 파일 11~20개, 12~32MB). 그런데 커밋 시간은 회차마다 선형으로 늘었다(재생 기준 0.9초 → 9.7초).

| 조정용 재생 | 커밋 시간 (회차 1 → 20) |
|---|---|
| `core.compression` 기본값 | 0.87 → 9.7초 |
| `core.compression=1` | 0.75 → 9.0초 |
| `core.compression=0` | 0.52 → 3.3초 (대신 `.git/objects` 340MB → 472MB) |
| **바뀐 게 없을 때의 커밋** | **0.66 → 8.5초** |

바뀐 게 없는데도 커밋이 실제 커밋만큼 오래 걸렸다. **원인은 JGit의 `add "."`이 바뀌지 않은 파일까지 매번 다시 읽고 압축하는 것**이다. JGit은 객체 ID를 알기 전에 압축부터 하므로, 내용이 같아도 비용이 그대로 든다. 그래서 비용이 월드 전체 크기에 비례했다.

**개선**: `status`(크기와 수정 시각 비교)로 바뀐 파일과 새 파일을 먼저 찾고, 그 파일만 `add`한다. 사라진 파일은 `rm --cached`로 처리한다(`HostLock.commitWorld`).

| | 개선 전 | 개선 후 |
|---|---|---|
| 조정용 재생 | 0.87 → 9.7초 | 0.49 ~ 1.2초 |
| 바뀐 게 없을 때 | 0.66 → 8.5초 | 29ms |
| **검증용 재생**(조정에 안 씀) | 실제 플레이 중 2.0 → 7.8초 | **0.37 ~ 0.91초, 늘어나는 추세 없음** |

## 저장소 크기와 전송량 (덤으로 확인)

- 기록한 원격 repo는 스냅샷 20개 만에 443MB였다. push마다 pack이 따로 쌓인 것이고, `git gc`를 하면 176MB, `--aggressive`는 172MB로 줄었다.
- **최신 월드 자체가 174MB이므로, gc 후에는 이력 비용이 거의 없다.** MCA는 청크마다 따로 압축하고 바뀌지 않은 청크의 바이트가 그대로 남아서, git delta가 바뀐 부분만 잡는다. GitHub는 서버에서 주기적으로 repack한다.
- 로컬 작업 repo에는 압축된 loose 객체가 쌓인다(재생 기준 340MB). 주기적인 로컬 gc가 필요하다(M2-b 이력 관리에서 다룸).
- push 전송량은 스냅샷당 15~25MB였다. JGit thin pack(`setThin(true)`)은 원격 증가량이 줄지 않고 push만 느려져서 되돌렸다(받는 쪽은 thin pack을 완성된 pack으로 저장하므로 이 측정으로는 전송량을 볼 수 없다는 한계가 있다). git CLI의 thin push도 15~18MB로 thin을 끈 경우와 비슷했다.
- 이 세션은 봇이 6초마다 400블록씩 이동하는 탐험 위주라 새 지형 데이터가 많다(월드 12MB → 174MB). 한곳에서 건축하는 일반적인 플레이의 전송량은 따로 확인해야 한다.

## 텍스트 변환(SNBT)이나 다른 오픈소스를 쓸 필요가 있는가

| 문제 | 텍스트 변환의 효과 | 판단 |
|---|---|---|
| 커밋 시간 | 원인이 JGit 사용 방식이었고 이미 해결됨. 변환은 저장을 멈춘 동안 청크를 파싱하고 직렬화하는 시간을 더할 뿐이다 | 불필요 |
| 저장소 크기 | gc 후 이력 비용이 이미 거의 0. 텍스트는 바이너리보다 몇 배 크다 | 불필요 |
| 전송량 | 청크 안에서 작은 부분만 바뀔 때 텍스트 delta가 압축 바이너리보다 작을 수는 있다. 아직 측정하지 않은 가설 | 건축 위주 워크로드에서 전송량이 문제로 확인되면 E1(A vs C′)로 검토 |
| 병합 | 호스트가 한 명뿐인 설계라 병합이 필요 없다 | 불필요 |

- 검토한 오픈소스: Querz/NBT(변환 시 NBT/MCA 처리용, 변환을 안 하면 불필요), restic/borg 같은 중복 제거 백업 도구(git delta가 이미 같은 효과를 내고, 바꾸면 push 기반 락을 잃음), Git LFS(파일을 통째로 저장해서 delta가 없어 더 나쁨).

## 결론

- 커밋 시간 문제는 해결했다: 바뀐 파일만 stage하면 월드 크기와 관계없이 1초 안팎이다(검증용 세션으로 확인).
- 저장 형식 변환은 지금 필요하지 않다. 다시 검토할 조건은 일반적인 건축 플레이에서 push 전송량이 문제로 측정될 때다.
